4. Current logging — electron/logger.ts (37 lines, full file read)
API surface (lines 28-37):


export const logger = {
  info(message: string): void
  warn(message: string): void
  error(message: string, err?: unknown): void
}
Three levels only — no debug, no trace, no structured/contextual logging (no ability to attach a payload object, correlation ID, or jobId as a separate field — everything is string-interpolated into message by each call site).

Output destination: File only — appendFile(logFilePath(), line, 'utf-8') (line 17), where logFilePath() (line 9-11) is userData/logs/wpa-<YYYY-MM-DD>.log, one file per calendar day, lazily mkdir'd on first write (lines 13, 19-24). Not also written to console/stdout — so in dev, nothing appears in the terminal/DevTools unless the developer separately tails the log file. Every write failure is silently swallowed (.catch(() => {}), line 17, and the mkdir catch at line 24) — a disk-full or permissions failure is invisible.

Format: Plain text, not structured/JSON: [${new Date().toISOString()}] [${level}] ${message}\n (line 16). No JSON encoding, no separate fields for level/timestamp/context that a log viewer or aggregator could parse reliably — e.g. a message containing \n would corrupt the line-based format. error() appends err.message (or String(err)) inline into the same string (lines 32-35), discarding the stack trace entirely — no err.stack is ever logged anywhere in the codebase.

Missing for objective's "Logging & Diagnostics" goals:

No structured/JSON output.
No log levels beyond info/warn/error (no debug for verbose diagnostics, no explicit "fatal"/"perf" tier).
No stack traces captured on error().
No performance/timing metrics as first-class fields — durations are manually string-interpolated per call site (e.g. processHandlers.ts:44,47 — Date.now() - startedAt computed ad hoc, not funneled through any shared metrics helper).
No resource/system reporting at all (no memory/CPU/disk-space logging anywhere in electron/).
No log rotation/retention policy beyond "one file per day" — old log files are never pruned.
No correlation between a jobId and its log lines as a structured field (jobId is just interpolated into the message string, e.g. preprocessHandlers.ts:208, 379-382).

Phase 11 Research Findings — Robustness, Diagnostics, and Temp-File Inventory
1. Crash/interruption recovery — what already exists
Batch registry persistence mechanism (apps/desktop/electron/services/batchRegistry.ts):

atomicWrite() (lines 45-49) IS crash-safe for a single file: it writes to path + '.tmp' then calls rename() to the final path. POSIX/APFS/NTFS rename is atomic, so a crash mid-write leaves either the old file intact or (post-rename) the new file intact — never a half-written file.
However, each mutating operation writes two separate files non-atomically as a pair: updateStage() (lines 125-138), renameBatch() (140-149), and setBatchMode() (156-165) each call atomicWrite(detailPath(id), updated) first, then separately readIndex()/writeIndex(index). If the app crashes between these two calls, the per-batch detail file (<id>.json) and the lightweight index.json summary can disagree — e.g., the Home screen's summary list (which reads only index.json via listBatches(), line 112-115) could show a stale status while getBatch() (117-123) returns the true, newer state. There is no reconciliation that detects/repairs this drift.
readIndex() (51-65) and getBatch() (117-123) both swallow all parse/read errors silently: a corrupt or unreadable index.json causes readIndex() to return { version, nextSeq: 1, nextTestSeq: 1, batches: [] } — i.e., the entire batch history silently disappears with no error surfaced to the user or logged as a corruption event (the catch {} at line 62-64 does not even call logger.error). A corrupt individual <id>.json similarly makes getBatch() return null (line 120-122) with no logged diagnostic.
Reconciliation at startup — does not exist. apps/desktop/electron/main.ts's app.whenReady() handler (lines 50-68) only registers IPC handlers and creates the window; it never calls listBatches()/getBatch() to inspect existing batches. Grepping the whole apps/desktop/electron tree for whenReady, reconcile, orphan, stale, and status === 'running' turns up nothing that touches persisted batch state at launch. Consequence: if the app crashes or is force-quit while a stage's status is 'running' (set at preprocessHandlers.ts:220 / ringBraceletHandlers.ts:162, or implicitly for watch), that stage record is left permanently at status: 'running' in <id>.json on disk. computeCurrentStage() (batchModel.ts:45-54) will keep resolving that stage as the batch's currentStage forever (a running stage always wins), and deriveBatchStatus() (batchModel.ts:64-73) will keep reporting the batch as 'in_progress'. There is no code path that ever flips it back — the batch just sits "running" indefinitely with no exposed recovery action. (The only thing that can rewrite it is the user manually starting a brand-new preprocessing/ring-bracelet job that reuses the same batchId, which will call updateStage(...,'running',...) again and eventually terminate normally — but nothing prompts the user to do this, and Preprocessing/Ring&Bracelet have no "resume" affordance at all, see §6.)

Watch Processing session files (apps/desktop/electron/ipc/sessionHandlers.ts): this stage has real crash-safety and its own reconciliation, unlike the registry:

session:save (lines 36-52) uses the identical write-tmp-then-rename atomic pattern (tmpPath = filePath + '.tmp', writeFile then rename, lines 43-45).
session:load (54-157) actively falls back to the .tmp file if the real file can't be read (lines 58-67) — recovering from a crash that happened between the writeFile and the rename call, which the batch registry's readIndex/getBatch do not do.
It also does a genuine reconciliation pass: any processingQueue item marked 'complete' has its exported output file re-verified to exist on disk (lines 126-141); if missing, it's reset to 'queued' so it gets reprocessed (resetCount++, line 137-138). This is the one place in the whole app with real "did this actually finish" verification against the filesystem.
Session saving is autosaved continuously by the renderer: apps/desktop/src/hooks/useSessionAutosave.ts debounces a session:save call 400ms after any change to annotations/currentIndex/mode/queueItems (lines 12-55), and items still 'processing' at save time are downgraded to 'queued' (line 25) so a crash mid-processing-item doesn't strand it. This is a real, working "safely resume work" mechanism for Watch — see §6.
2. Python subprocess failure handling
Both handlers share an identical structure and identical gaps.

apps/desktop/electron/ipc/preprocessHandlers.ts:

Spawn failure (ENOENT, permission denied, bad interpreter path) is caught synchronously at the spawn() call site itself (try/catch, lines 182-193) — this is a distinct code path from the 'error' event.
child.on('error', ...) (lines 386-407): fires for post-spawn errors (e.g., EPIPE on a broken pipe). It logs, clears activeJob = null (389), writes stage status 'failed' with err.message (393-395), and notifies the renderer with spawnError set (397-406). This correctly frees the activeJob slot for a future run.
child.on('close', ...) (lines 307-383): the sole source of truth for completion. It classifies outcome only as cancelled (code === EXIT_CANCELLED, i.e. 3), or job.fatalError ? 'failed' : 'completed' (line 331) — any other non-zero/unexpected exit code (segfault, OOM-killed process, Python traceback exit code 1) is NOT specially handled; it falls into 'completed' unless a 'fatal' NDJSON event happened to be emitted first. If the process is killed by a signal (e.g., OS OOM killer) with no NDJSON 'fatal' event, the batch stage is recorded as 'completed' even though nothing succeeded, because job.succeeded/job.failed and the per-image reconciliation (337-347) only reflect whatever NDJSON events did arrive.
No timeout/watchdog exists anywhere. There is no setTimeout, no hang-detection, nothing that inspects whether the child has stopped emitting NDJSON/heartbeat events. Grepping preprocessHandlers.ts/ringBraceletHandlers.ts for setTimeout|setInterval|watchdog|timeout returns zero matches. If the Python process hangs (e.g., stuck in a native library call, GPU deadlock) without exiting, child.on('close') never fires, activeJob is never cleared, and preprocess:start's guard (if (activeJob !== null || jobStarting), line 114) will reject every future preprocessing run until the user force-quits and restarts the Electron app. The only mitigation is preprocess:cancel (lines 425-443), which is purely cooperative (writes {"cmd":"cancel"} to stdin) — if the hang is inside a stage with no cancellation checkpoint (e.g., BiRefNet model loading, explicitly called out as "the one genuinely uninterruptible span" in electron_runner.py:389-391), cancel does nothing and the slot stays blocked forever.
apps/desktop/electron/ipc/ringBraceletHandlers.ts — byte-for-byte the same architecture and the same gaps:

Spawn failure: try/catch at spawn call, lines 133-141.
child.on('error', ...): lines 301-321, identical shape/behavior to preprocessHandlers.
child.on('close', ...): lines 241-298, same "any other exit code silently becomes 'completed' unless a fatal event fired" gap.
No timeout/watchdog: same absence, activeJob (line 34) can be permanently occupied by a hung runner.py, blocking ring-bracelet:start (line 71's guard) until app restart.
3. Corrupt image / missing file handling per pipeline
Watch Processing (packages/processing + apps/desktop/electron/ipc/processHandlers.ts + queueHandlers.ts) — already fully per-image isolated, at two layers:

packages/processing/src/processing/processWatch.ts (lines 8-46) does no internal try/catch; it throws synchronously (e.g. throw new Error("Input image must be a PNG") at line 12, or lets sharp() reject on a corrupt/unreadable file at line 9).
apps/desktop/electron/ipc/processHandlers.ts's runProcessWatch() (lines 16-52) wraps that call in try/catch (33-51) and classifies the error via classifyError() (lines 7-14, matching ENOENT/EACCES/EPERM/PNG-validity messages into user-facing strings), returning { ok: false, sku, error } rather than throwing.
apps/desktop/electron/ipc/queueHandlers.ts's processNext() (lines 45-80) has a second belt-and-suspenders try/catch (54-74) around the runProcessWatch call, marks only that queue item 'failed' (67-68/71-73), and always calls void processNext() again (79) to continue the queue — one bad image never stops the batch.
Universal Preprocessing (preprocessing/UBG/electron_runner.py): per-image isolation exists via a single broad try/except Exception as exc around the entire per-image pipeline (lines 449-690), emitting {"type":"error", ..., "fatal": False} (682-689) and incrementing failed (690) rather than aborting the loop, with a finally block (692-695) that always cleans up that image's temp upscaled file regardless of success/failure/cancellation. The loop continues to the next image. Only true startup-level failures (missing input dir, zero images found, BiRefNet failing to load) short-circuit the whole run via {"type":"fatal"} + early return 1 (lines 311, 323, 400, 403).

Ring & Bracelet (preprocessing/RingBracelet/runner.py): identical pattern — _process_one() (lines 112-153) "Raises on failure" (per its own docstring, line 113) and is called inside a try/except Exception as exc in the main loop (lines 194-215), emitting {"type":"error", "fatal": False} (207-214) and incrementing failed (215) without stopping the batch.

Conclusion for Q3: all three pipelines already isolate a single corrupt/unreadable image and continue the batch — this is existing, consistent behavior, not a gap. The gap is upstream of per-image handling: a process crash/OOM/hang (see §2) is not distinguishable from "all images happened to fail," and there's no verification that an image marked 'completed' still exists on disk later (unlike the Watch session reconciliation in §1).

Verdict: I disagree that this is a per-image model reload/reinit, and disagree it's a growing-list/Python-object leak. So: no code path reloads/reinitializes any model per image. All three caches behave correctly.

No GPU memory cleanup on MPS, anywhere — this is the real finding:

torch.cuda.empty_cache() appears exactly 3 times in the whole tree (sam_segmenter.py:146, upscaler.py:263, upscaler.py:268) — and every single one is inside a CUDA-OOM exception handler. There is no torch.mps.empty_cache() call anywhere in preprocessing/UBG/ (confirmed by grep across all .py files), despite torch.mps being imported and read from in electron_runner.py:158-166 (_mps_stats() reads torch.mps.current_allocated_memory() and torch.mps.driver_allocated_memory() purely for reporting, never for cleanup).
There is no del of intermediate tensors, no gc.collect(), anywhere in the pipeline stages.
Nothing "grows" as a Python list/cache across images that would explain the timing pattern — image_records (electron_runner.py:434, 672-677) is pure bookkeeping (dicts of ints), not GPU-resident, and is only appended to, never fed back into inference.
The actual production profiling logs in the repo confirm and sharpen your Phase 10G numbers. preprocessing/UBG/profiling/profile_20260717_123323.txt is very likely the exact run you're describing — its "Per-image timings" table is:

mps_current_mb (what PyTorch's allocator considers "in use") stays modest (~1.2 GB), but mps_driver_mb (what the Metal driver has actually claimed and not released) balloons to 16.5 GB by the end of a 4-image batch. Two other profiling files corroborate this is not a one-off:

profile_20260716_115450.txt and profile_20260714_133048.txt (watch plugin, requires_masks=True, so SAM runs) show the sam column escalating instead: 6287 → 5608 → 6584 → 5618 → 8072 → 9208 → 18243 → 66308 ms across an 8-image batch — a >10x blowup by the last image, with mps_driver_mb: 14012.7 / 14268.7 at batch end.
profile_20260716_174752.txt (a batch that ran scale_factor=1, so upscale is a no-op copy and image sizes/stage costs stay flat throughout) shows no escalation at all (upscale 17361/16365/17600/16672/16646/16500 ms — essentially constant) and correspondingly modest mps_driver_mb: 5581.4.
Grounded hypothesis: the escalation tracks whichever stage is doing real MPS-heavy tensor work (Real-ESRGAN tiled forward passes when scale>1, or SAM2's per-image grid of points_per_side² forward passes when a mask-consuming plugin is active) — never BiRefNet specifically, and never present when GPU work is trivial (scale_factor=1, no masks). Because torch.mps.empty_cache() is never called between images (or between stages), PyTorch's MPS caching allocator keeps accumulating driver-level memory blocks release-to-release across the whole batch instead of returning them to the OS/Metal driver. On Apple Silicon's unified memory architecture this manifests as: (a) growing allocator search/fragmentation overhead on each new tensor allocation, and (b) system-wide memory pressure that can trigger macOS memory compression/swapping for the whole process (Electron main process included), both of which would slow every subsequent GPU-bound stage call, cumulatively, regardless of which stage happens to be GPU-heavy in that particular batch. This is consistent with all three profiling files above. It is not a model-reload issue (ruled out directly — the caches are correct) and not a naive Python object/list leak (RSS actually decreases image-to-image in the after_save column of profile_20260717_123323.txt: 599.7 → 418.4 → 330.5 → 319.4 MB — so process heap memory is fine; it's the MPS/Metal driver layer that's accumulating).

Stages that touch GPU/model per iteration: upscale_image() call at electron_runner.py:459-463 → services/upscaler.py:239 (upsampler.enhance(...), no cleanup after); remover.remove_background() at electron_runner.py:514-525 → background_remover.py:184-186 (torch.inference_mode() block, no cleanup after); segment_image() at electron_runner.py:563-571 → sam_segmenter.py:140 (generator.generate(...), no cleanup after).
The one and only place any GPU cache is ever cleared is CUDA-OOM-specific (sam_segmenter.py:146, upscaler.py:263/268) — there is no equivalent unconditional/periodic torch.mps.empty_cache() call anywhere, which is the gap a fix would target (not now — just characterized per your instructions).

4. Plugin registration mechanism
Not a registry/dispatch table — it's dynamic module import by naming convention, in services/plugin_loader.py:9-16:


def load_plugin(object_type=None):
    safe_type = "".join(ch.lower() if ch.isalnum() else "_" for ch in (object_type or PIPELINE.object_type)).strip("_") or "generic"
    try:
        return importlib.import_module(f"plugins.{safe_type}")
    except ModuleNotFoundError:
        return importlib.import_module("plugins.generic")
There's no registry dict, no if/elif chain, no explicit list of valid plugins anywhere — object_type (a free-form CLI string, electron_runner.py:211-212) is sanitized and used directly as a Python module filename under plugins/. If plugins/<object_type>.py doesn't exist, it silently falls back to plugins/generic.py.

Each plugin module is a flat file exposing two things by convention (not an enforced interface/ABC): a CONFIG dict and a process(image, masks) -> dict function. CONFIG["requires_masks"] (only set True in plugins/watch.py:11; absent/False in bracelet.py, generic.py, ring.py) is read reflectively via getattr(_plugin, "CONFIG", {}).get("requires_masks", False) in electron_runner.py:347 to decide whether SAM2 segmentation runs at all for the batch.

To add a new plugin today, the only required change is: drop a new plugins/<name>.py file implementing CONFIG (dict) + process(image, masks) (function returning at minimum a dict with an optional "processed_image" key). No other file needs to change — plugin_loader.py, electron_runner.py, and services/plugin_loader.py's import path all work automatically off the --object-type string. This is the "pluggable" part of the system, and it is genuinely low-friction. The gaps for Phase 11 to note: (1) no validation that a plugin module actually implements the expected interface — a malformed plugin fails at call time with an AttributeError, not at load time; (2) no discovery/listing mechanism (nothing enumerates plugins/*.py to tell the Electron UI what object types exist — that list must be hardcoded on the TypeScript/UI side separately, which is itself a duplication risk); (3) the "requires_masks" capability flag is the only declared capability — there's no broader plugin manifest/schema, so any future per-plugin needs (e.g. "requires upscale," "custom output naming") would need ad hoc getattr(..., default) reads added to electron_runner.py one at a time, the same way requires_masks was.

5. Temp/intermediate file usage
No tempfile/mkdtemp/hardcoded /tmp usage anywhere in either preprocessing/UBG/ or preprocessing/RingBracelet/ (confirmed via grep — zero matches). All "temp" handling is manual, output-directory-scoped:

electron_runner.py:377-379: temp_dir = output_dir / "temp", created alongside output_dir at batch start.
electron_runner.py:444: per image, temp_path = temp_dir / f"{input_path.stem}_upscaled.png" — this is the upscaled-but-not-yet-background-removed intermediate.
electron_runner.py:692-695: in the finally block of the per-image try, if temp_path.exists(): temp_path.unlink() — cleaned up after every image (success, failure, or mid-loop break from cancellation), so this specific intermediate does not accumulate across a run. Note it's cleaned per-image, not batch-end, so if the process crashes/is killed hard (not the cooperative-cancel path) mid-image, a stray _upscaled.png could be left in output_dir/temp/, and output_dir/temp/ itself is never removed (empty dir persists after every batch).
stage0/background_remover.py:281, 293, 316-317 (process_folder(), the older non-Electron code path) does the same temp/ + unlink pattern independently — this function appears to be a legacy/manual entry point separate from electron_runner.py, duplicating temp-handling logic a second time.
electron_runner.py:352-357: profiling/profile_<timestamp>.txt is written every single run and never cleaned up — 36 files currently in preprocessing/UBG/profiling/ going back to July 1, ranging ~600 bytes to ~6.5 KB each. Individually small, but this is unbounded accumulation with no retention/rotation policy — a genuine finding for "temp-file-management cleanup" even though these are diagnostic, not scratch, files.
RingBracelet/runner.py has no temp files at all — _process_one() (runner.py:112-153) writes only the two final named deliverables (;frontFullImage.png, ;frontImage.png) directly to output_dir, nothing intermediate.
Genuinely temporary: output_dir/temp/*_upscaled.png (per-image, cleaned up per-image in the happy/error path, but the empty temp/ directory and any crash-orphaned files are not swept).
Not temporary, but arguably should be pruned/managed: preprocessing/UBG/profiling/*.txt (accumulates indefinitely, one file per run, no cap).
Final deliverables: output_dir/<stem>.<suffix> (UBG) and output_dir/<stem>;frontFullImage.png / ;frontImage.png (RingBracelet).

6. Caching
Two distinct kinds of caching exist, both in-process/in-memory, per-run only — nothing persists to disk as a cache across separate runs beyond the model weight files themselves (which are static assets, not a cache layer):

In-memory model caches (within a single batch run): _GENERATOR/_GENERATOR_KEY module globals for SAM2 (sam_segmenter.py:24-28) and _UPSAMPLER/_UPSAMPLER_KEY module globals for Real-ESRGAN (upscaler.py:111-112), both keyed on config parameters + device, both correctly reused across every image in a batch. These die with the process — a new electron_runner.py invocation always rebuilds both from scratch (SAM2 checkpoint load off disk again, Real-ESRGAN weights load off disk again), so there is no cross-run cache.
No download/weights cache: no cache_dir, HF_HOME, TORCH_HOME, or huggingface/torch.hub references anywhere in preprocessing/UBG/ or preprocessing/RingBracelet/ (confirmed via grep). BiRefNet and Real-ESRGAN weights are vendored directly as static files under models//stage0/; SAM2's checkpoint is fetched once via download_models.py (a plain urllib.request download to a fixed models/sam2/ path, download_models.py:15-19 skips re-download if the file already exists — that's the only "cache" in the download sense, and it's a simple existence check, not a real cache layer).
No computation/result caching of any kind (e.g. no memoization of BiRefNet masks, no on-disk intermediate cache keyed by image hash) — every image, every run, redoes 100% of the pipeline from raw pixels.
Notable duplication, not caching: BiRefNet_dynamic.safetensors (424 MB) exists twice on disk — once at preprocessing/UBG/stage0/BiRefNet/BiRefNet_dynamic.safetensors (the path actually used by background_remover.py's default model_root resolution, background_remover.py:102-107) and once at preprocessing/UBG/models/BiRefNet_dynamic/BiRefNet_dynamic.safetensors (unused by the runtime code path, only ever loaded if --birefnet-model-root is explicitly overridden to point there) — 424 MB of pure redundant storage, worth flagging under Phase 11's disk-I/O/temp-management objective even though it's not "temp" per se.

Blurry / accidental-looking boundaries (the important part):

components/preprocessing/ folder name is now a misnomer for half its contents. ThumbnailGrid.tsx, ThumbnailCell.tsx, and BeforeAfterSlider.tsx are structurally-shared, stage-agnostic presentational primitives (each has code comments explicitly designed to be stage-decoupled), yet they live inside a folder named after one specific stage. Ring/Bracelet has to reach across the stage boundary with ../preprocessing/... imports to use them. This is the single clearest signal that a components/shared/ or components/media/ (or similar cross-stage) directory is missing.

CSS is reused across the stage boundary by direct cross-folder import, not by a shared primitive. components/ringBracelet/RingBraceletImagePreviewPanel.tsx:6 imports styles from '../preprocessing/ImagePreviewPanel.module.css' and components/ringBracelet/RingBraceletRunWorkspace.tsx:9 imports styles from '../preprocessing/PreprocessingRunWorkspace.module.css'. Neither Ring/Bracelet component has its own .module.css file at all (confirmed: components/ringBracelet/ contains only 2 .tsx files, no CSS). Both source files have comments acknowledging this ("Reuses ImagePreviewPanel's stylesheet directly... no parallel CSS file") — it's a deliberate shortcut, but it means Ring/Bracelet's presentation is literally not self-contained; renaming/moving the Preprocessing CSS file would silently break Ring/Bracelet's styling.

components/PreprocessingProgress.tsx lives at the top-level components/ (not components/preprocessing/) specifically because it's shared — used by both preprocessing/PreprocessingRunWorkspace.tsx:3 and ringBracelet/RingBraceletRunWorkspace.tsx:3. This is actually the correct pattern (shared things live outside the stage-named folder) but it's inconsistent with items 1–2 above, where other equally-shared components (ThumbnailGrid, BeforeAfterSlider) were left inside preprocessing/ instead of being promoted alongside it. There's no single convention currently — some shared code got promoted out, some didn't.

screens/BatchDetails.tsx (605 lines) is a genuine cross-stage god-screen, not cleanly attributable to any one stage. It directly imports from all three: PreprocessingSummary (top-level, preprocessing-only), ThumbnailGrid/ImagePreviewPanel (preprocessing), RingBraceletImagePreviewPanel (ringBracelet), PreprocessingJobContext+RingBraceletJobContext types, plus ad hoc Watch-session loading via raw session:load IPC calls (BatchDetails.tsx:213-227) since Watch has no batch-registry image sync of its own (per its own comment at BatchDetails.tsx:179-185). Its sibling components/PreprocessingSummary.tsx imports it from ./preprocessing/EditingHandoffDialog (PreprocessingSummary.tsx:2), so the naming ("Preprocessing"-prefixed component reaching into a differently-scoped subfolder) reads as more historical-accretion than deliberate structure.

4. Context/state architecture
Four providers in context/:

Context	Responsibility	Notes
PreprocessingJobContext.tsx (240 lines)	Owns preprocessing job lifecycle: phase/progress/images/errors/cancel state; subscribes to preprocess:event/preprocess:done IPC	App-lifetime provider (mounted once in App.tsx:593)
RingBraceletJobContext.tsx (204 lines)	Owns ring/bracelet job lifecycle; subscribes to ring-bracelet:event/ring-bracelet:done	App-lifetime provider (App.tsx:594)
AnnotationContext.tsx (118 lines)	Owns Watch annotation state: current index, per-SKU annotations, guide mode, submit/navigate	Mounted per-batch inside AnnotationWorkspace
QueueContext.tsx (93 lines)	Owns Watch export-queue state (optimistic + confirmed items), subscribes to queue:update IPC	Mounted per-batch inside AnnotationWorkspace
Divergence: PreprocessingJobContext and RingBraceletJobContext are near-identical hand-copied state machines, explicitly documented as such in their own source.

RingBraceletJobContext.tsx:57-62: "Mirrors PreprocessingJobProvider's structure exactly (mounted for the lifetime of the app...) — see that file for the fuller rationale."
RingBraceletBatchSync.tsx:10-12: "Mirrors PreprocessingBatchSync exactly."
Both contexts independently declare: the same phase: 'idle'|'running'|'done' shape, the same cancelPhase state machine (actually literally shared via CancelPhase imported from PreprocessingJobContext at RingBraceletJobContext.tsx:3), the same jobIdRef pattern to avoid resubscribing, the same start/cancel/reset callback shapes, the same event-subscription cleanup pattern, and near-identical reducer-style switch blocks over 'start'|'progress'|'complete'|'error'|'fatal'|'cancel_requested' event types (PreprocessingJobContext.tsx:104-163 vs RingBraceletJobContext.tsx:79-136).
The differences are narrow and structural: Preprocessing's images have stage/outputPath/durationMs; RingBracelet's have frontFullImage/frontImage/detected instead. Preprocessing has initializing/heartbeat event types RingBracelet doesn't. Preprocessing's start() returns Promise<boolean>; RingBracelet's returns Promise<void>.
RingBraceletJobContext.tsx:7-9 explicitly explains why it wasn't factored into a shared hook: "Independent from PreprocessingImageStatus (same five values, deliberately not imported) — keeps this context decoupled from Preprocessing's, per Phase 10's 'keep preprocessing and asset generation cleanly separated.'" So the duplication is a deliberate past decision, not an oversight — but it is ~140 lines of near-identical lifecycle/subscription/reducer boilerplate duplicated verbatim across the two files, which is exactly the kind of thing a shared createJobContext(eventChannel, doneChannel, imageReducer) factory (parameterized only by the event channel names and the per-event-type image-state mapper) could collapse into one implementation with two thin instantiations — while still preserving the "decoupled image-status types" goal, since the factory's generic type parameter would keep each instantiation's ImageState shape independent.
AnnotationContext/QueueContext are Watch-only, structurally different from the two job contexts (no IPC event subscription pattern, form/session-state shaped rather than job/event-stream shaped) — not part of this duplication.
